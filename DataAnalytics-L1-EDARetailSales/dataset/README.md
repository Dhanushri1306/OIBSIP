\# Indian E-Commerce Customer \& Order Intelligence Dataset



A large-scale, internally-consistent \*\*synthetic\*\* dataset simulating a mid-size Indian

e-commerce marketplace: customers, products, orders, order items, payments, shipments,

returns, reviews, and marketing campaigns, spanning \*\*2023-01-01 to 2025-12-31\*\*.



\---



\## 1. Dataset Overview



This dataset was built to give data scientists a realistic, relationally-consistent

sandbox for practicing the full spectrum of e-commerce analytics and machine learning â€”

without any of the privacy, licensing, or access restrictions that come with real

transactional data.



Every table is generated programmatically from a single reproducible script

(`generate\_dataset.py`), with \*\*hidden latent variables\*\* (customer segment, product

category baseline return rate, channel quality, seasonality, festivals) that drive

believable relationships between tables, rather than independently-randomized columns.



\*\*Scale:\*\*

\- 25,000 customers

\- 550 products across 22 categories

\- 100,000 orders (2023-01-01 â†’ 2025-12-31)

\- \~254,000 order line items

\- 100,000 payment records

\- \~89,700 shipments

\- \~12,000 product-level returns

\- \~77,500 customer reviews

\- 151 marketing campaigns across 10 channels

\- 15 Indian states, 31 Indian cities

\## 3. Data Generation Methodology



\*\*This is a 100% synthetic dataset.\*\* It does not contain, was not derived from, and does

not represent any real company's data, any real individual's personal information, or any

real transaction. All customer names, exact addresses, and identifiers are fabricated.

City/state/pincode-prefix values reference real Indian geography for realism, but no

real customer or business is represented.



The dataset is produced by a single deterministic Python script (seed = 42) using

`numpy`, `pandas`, and `faker`. Generation proceeds in dependency order so that every

downstream table is derived from â€” and stays consistent with â€” the tables before it:



1\. \*\*Customers\*\* are generated first, with a segment (`Premium`/`Regular`/`Budget`/`New`),

&#x20;  an acquisition channel, a signup date, and a hidden "activity span" that determines how

&#x20;  long they stay engaged before churning.

2\. \*\*Products\*\* are generated with category-specific price ranges, margins, and baseline

&#x20;  return-rate propensities.

3\. \*\*Orders\*\* are generated by first deciding \*how many\* orders each customer places

&#x20;  (a function of their segment and channel quality), then sampling \*when\* each order

&#x20;  happens from a daily demand curve that layers weekday/weekend effects, monthly

&#x20;  seasonality, year-over-year growth, and Indian festival spikes (Diwali, Dussehra/

&#x20;  Navratri, Holi, Eid, Christmas/New Year, Republic Day, Independence Day, and major

&#x20;  sale periods).

4\. \*\*Order items\*\* are generated per order (1-5 line items), and order-level `subtotal`,

&#x20;  `tax\_amount`, `shipping\_fee`, and `final\_amount` are \*\*recomputed from the actual line

&#x20;  items\*\* â€” never generated independently.

5\. \*\*Payments\*\* inherit the customer's preferred method (70% of the time) with realistic

&#x20;  status outcomes tied to `order\_status`.

6\. \*\*Shipments\*\* are generated only for orders that reach fulfillment; delivery speed

&#x20;  depends on `shipping\_method` and whether the destination is in the same logistics

&#x20;  region as the assigned warehouse.

7\. \*\*Returns\*\* are sampled per order item with a probability driven by the product's

&#x20;  category baseline return rate, sharply elevated for orders already flagged

&#x20;  `Returned`.

8\. \*\*Reviews\*\* are sampled from delivered/returned order items, with the star rating

&#x20;  centered on the product's average rating and penalized (with noise) by delivery delay

&#x20;  and return status.

9\. \*\*Marketing campaigns\*\* are generated per month/channel, and their `conversions` and

&#x20;  `revenue\_generated` are aggregated \*\*from the actual orders table\*\* rather than

&#x20;  invented â€” only the cost/ROI model uses channel-level assumptions.

10\. \*\*Customer aggregates\*\* (`total\_orders`, `total\_spend`, `average\_order\_value`,

&#x20;   `last\_order\_date`, `customer\_status`, `loyalty\_tier`) are recomputed at the end from

&#x20;   the real order history, not generated independently.

\## 4. Features



Selected columns worth calling out:



\- \*\*`customers.customer\_status`\*\* â€” derived rule: `Never Purchased` (0 orders),

&#x20; `Active` (last order â‰¤ 90 days before 2025-12-31), `At Risk` (â‰¤ 180 days),

&#x20; `Churned` (> 180 days). A ready-made, documented churn label.

\- \*\*`orders.final\_amount`\*\* â€” reconciled bottom-up from `order\_items.item\_revenue`

&#x20; plus shipping and tax; always ties out (see validation report).

\- \*\*`order\_items.profit`\*\* â€” `item\_revenue - item\_cost`, useful for margin analysis.

\- \*\*`shipments.delayed\_flag`\*\* â€” 1 if `actual\_delivery\_date > expected\_delivery\_date`.

&#x20; The clean target for delivery-delay prediction (see the anti-leakage note below).

\- \*\*`products.return\_rate\_baseline`\*\* â€” the hidden simulation parameter behind

&#x20; category-level return propensity; a useful sanity-check feature but see the leakage

&#x20; note in Section 8.

\## 6. Data Quality



The dataset ships with an automated validation suite (`dataset\_validation\_report.csv`,

43 checks, \*\*all passing\*\* as of the published version) covering:



\- Row-count and cardinality requirements (customers, products, orders, states, cities,

&#x20; categories, payment methods, channels, shipping methods)

\- Primary-key uniqueness across all 9 tables

\- Foreign-key integrity across every relationship (zero orphan rows)

\- Valid date ranges (no dates outside 2023-01-01 to 2025-12-31)

\- Non-negative prices, quantities, and monetary amounts

\- \*\*Order-total reconciliation\*\*: `orders.subtotal` == `SUM(order\_items.item\_revenue)`

&#x20; for every order, within a 0.5 rounding tolerance

\- \*\*Payment reconciliation\*\*: `refund\_amount` never exceeds `final\_amount`

\- \*\*Return reconciliation\*\*: `refund\_amount` never exceeds the underlying `item\_revenue`

\- \*\*Shipment date consistency\*\*: `actual\_delivery\_date >= dispatch\_date` and

&#x20; `expected\_delivery\_date >= dispatch\_date` for every shipment

\- \*\*Customer aggregate consistency\*\*: `customers.total\_spend` independently recomputed

&#x20; from order history and compared against the stored value

\- Valid city/state combinations (no impossible geography)



A small, realistic amount of MCAR (missing-completely-at-random) data is present in a

few non-critical columns (`customers.age` \~1%, `customers.preferred\_device` \~0.5%,

`products.rating\_average` \~0.8%, `customer\_reviews.review\_sentiment` \~0.3%) to mirror

real-world data collection gaps â€” nothing else is randomly nulled.

\## 7. Limitations



\- \*\*This is synthetic data.\*\* While the generation logic encodes realistic relationships

&#x20; (seasonality, festival effects, category-level pricing/returns, channel quality,

&#x20; churn dynamics), it is a simplified model of real consumer behavior and will not

&#x20; capture every nuance, correlation, or edge case present in real transactional data.

\- Product names, brand names, and campaign names are synthetically generated and do not

&#x20; reference real brands, even where a name may coincidentally resemble one.

\- Marketing funnel metrics (`impressions`, `clicks`) are illustrative, derived backward

&#x20; from channel-level CTR/CVR assumptions rather than measured â€” treat them as

&#x20; reasonable placeholders, not ground truth.

\- The dataset represents a single simulated business; it should not be used to draw

&#x20; conclusions about real Indian e-commerce market size, real company performance, or

&#x20; real consumer demographics.

\## 8. Anti-Leakage Notes for ML Use



When building predictive models, be mindful of columns that would not be legitimately

available at prediction time:



\- \*\*Delivery delay prediction\*\* (`shipments.delayed\_flag`): do \*\*not\*\* use

&#x20; `actual\_delivery\_date` or `delivery\_days` as input features â€” both are only known

&#x20; \*after\* the outcome you're predicting. Use `dispatch\_date`, `expected\_delivery\_date`,

&#x20; `shipping\_method`, `warehouse\_city`, and `delivery\_city` instead.

\- \*\*Return prediction\*\*: avoid using `returns.csv` fields as features for a model whose

&#x20; target is "will this order/item be returned" â€” that's the label source. Similarly,

&#x20; `products.return\_rate\_baseline` is the hidden simulation parameter that \*generated\*

&#x20; the label; using it as a feature will produce unrealistically strong (leaky) results

&#x20; in a way real-world data would not support. It's included for transparency/debugging,

&#x20; not as a recommended model feature.

\- \*\*Churn prediction\*\*: `customer\_status` is derived from `last\_order\_date`, which is

&#x20; itself derived from the full order history â€” make sure your feature set only uses

&#x20; information available \*before\* the cutoff you're predicting from (e.g., build features

&#x20; from orders before a chosen "as of" date, and predict status after it).

\- \*\*Revenue/CLV prediction\*\*: `orders.final\_amount` and `customers.total\_spend` are

&#x20; reconciled from `order\_items` â€” don't feed `order\_items` for the \*same\* order into a

&#x20; model predicting that order's total.
